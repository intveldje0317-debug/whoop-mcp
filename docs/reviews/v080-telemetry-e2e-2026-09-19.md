# Telemetry End-to-End Verification

## Scope

Tested the local v0.8.0 implementation on the v0.7.1 baseline against the
deployed Cloudflare Worker and D1 database. Package metadata remains 0.7.1,
so events correctly report that version. No version bump or publication occurred.

Endpoint: `https://whoop-mcp-telemetry.whoop-ai-mcp.workers.dev/events`.
The earlier TLS failure resolved; no TLS verification bypass was used.

## Synthetic Test

- Compiled MCP server and real telemetry sender delivered synthetic profile
  success, handler-error and invalid-output events through HTTPS to D1.
- Synthetic `serve` and `setup` command events used the same real sender.
- All five sends returned 204 within the unchanged 500 ms deadline:
  328, 83, 89, 78 and 331 ms. This small single-location sample does not
  establish global latency guarantees.
- Exact five-field payloads were checked. No WHOOP requests were made.
- Opt-out, DO_NOT_TRACK, aggregate privacy, CLI status and doctor added no counts.
- Unknown tools and SDK-invalid inputs did not emit events.
- Invalid names/fields/JSON, oversized bodies, unsupported media/methods and
  public read routes were rejected without database writes.
- The live limiter returned 429 after 54 additional malformed requests.
- Remote rows contained only day, version, kind, name, outcome and count.

The first harness attempt used an ID that the schema permits. The test fixture
was corrected to use spaces; this was not a product bug. Its pending send timed
out during rollback and produced no stored event.

## Claude Desktop

The user explicitly approved a temporary switch from `npx -y whoop-ai-mcp`
to the compiled local entry point, with explicit telemetry opt-in and endpoint.
Credentials were preserved without printing them. A private backup was retained.

The first attempt still ran the published connector. After a full restart,
the local connector process and a new successful startup event were verified.
The user then reported a tool-use card and ran a weekly health review. D1 deltas:

| Event | Outcome | Count Added |
| --- | --- | --- |
| `serve` | success | 1 |
| `get_weekly_summary` | success | 1 |
| `get_recovery_collection` | success | 1 |
| `get_sleep_collection` | success | 1 |
| `get_workout_collection` | error | 2 |

The `get_profile` success count did not increase; that particular Desktop call
is not verified. The workout errors were recorded correctly, but their underlying
cause was not investigated in this telemetry test. Desktop logs were inspected
only through sanitized process/lifecycle/tool-call metadata, not health results.

## Restoration and Limitations

- Restored the original WHOOP Desktop command, arguments and environment exactly;
  preserved unrelated Desktop preference changes made during testing.
- Desktop must be fully restarted once more to load the restored configuration.
- Redeployed with `COLLECTION_ENABLED=0`; verified an empty 503 response.
- Final disabled Worker version: `6e039d6e-e389-47ea-b418-00e11ececd26`.
- Retained five synthetic events and six Desktop events as 11 aggregate counts
  across eight rows. Do not interpret these as organic usage. No rows were deleted.
- Live database-failure injection was not performed; the local built-Worker test
  covers generic storage failure. This hosted release gate remains open.
- Collector remains disabled; this test does not authorize a general rollout.

Result: synthetic delivery and manual Claude Desktop telemetry verified,
including successful and failed tool outcomes. Profile-specific verification,
live storage-failure verification and final rollout approval remain outstanding.

## Subsequent Data Cleanup (2026-09-19)

The owner explicitly requested removal of only the five synthetic events while
preserving actual Desktop activity. Removed the synthetic `setup` success and
three `get_profile` outcomes, and subtracted one synthetic `serve` success from
its shared aggregate. Verified every remaining row against the expected before/after
projection: six Desktop events across five rows remain. The two workout errors
were preserved. Ingestion stayed disabled. This updates the retained-data state,
not the historical verification results above; D1 recovery history may still
contain prior states within Cloudflare's backup window.

## Release Gate Follow-Up

Live storage-failure handling was subsequently verified using a temporary Worker
deployment with no D1 binding and ingestion enabled. A synthetic request returned
an empty, non-cacheable 503. Since no DB was bound it could not write an event.
The original disabled configuration was restored in `finally`, and every remote
aggregate was compared before/after: all six actual Desktop events were unchanged.
This closes the previously outstanding live storage-failure gate without deleting
or modifying metrics. Consent-based collector activation at release was approved.
